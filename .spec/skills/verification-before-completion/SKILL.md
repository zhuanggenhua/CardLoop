# Verification Before Completion（完成前验证）

## 铁律

没有新鲜验证证据，不得声称完成、修好或通过。

## 验证步骤

1. 识别：哪条命令、测试、截图、Unity 状态、数据记录或文档链接能证明本轮目标？
2. 裁决范围：验证范围必须匹配本轮目标和用户授权；“完整”只表示覆盖本轮声称，不表示默认跑全仓、全量 Unity 回归或端到端测试。
3. 执行：运行该范围内最低足够的验证或读取真实证据。
4. 阅读：看退出码、失败数、关键输出、目标结果，不只看“无报错”。
5. 声明：只按证据说话；未覆盖的地方列 known gaps。

## 提交 / 推送 / 上传口径

- 用户要求“看下修改没问题就提交 / 推送 / 上传”时，默认目标是审查当前改动能否进入版本库，不是要求补齐完整质量验收。
- 用户说“检查修改没问题”或“修改没问题就提交 / 推送”时，“没问题”的默认定义是：当前已修改 / 待提交 diff 未发现明显阻塞进入版本库的问题。
- 最小检查范围包括：工作区和暂存区范围是否符合本轮目标、是否有冲突标记、敏感信息、明显语法 / 格式问题、明显反模式、直接 bug、以及项目已明确定义的提交前静态门槛。
- 只运行用户明确要求、项目收口门槛、已配置 git hook 或当前 diff 直接需要的最小检查。
- 不得把提交 / 推送 / 上传默认升级为全量 EditMode、PlayMode、端到端、截图验收或新增覆盖率工作。
- 如果现有证据不足以支撑“全部没问题”，应改成更窄结论，例如“静态规范检查通过、Unity 编译无错误；未跑全量回归”，而不是自行扩大验证范围。
- 放行结论只能表述为“未发现明显提交阻塞问题”或同等窄口径；不得表述为“全量没问题”“功能完整验证通过”或暗示未执行的重链路已经覆盖。

## 不足以证明完成

- “应该可以”。
- “日志没了”。
- “子 agent 说成功”。
- “只跑了局部命令却声称全量通过”。
- “修了相邻问题，但没回到用户原始症状”。

## 文档/规范任务验收

- 根入口能指向 `.spec`。
- `.spec/knowledge/README.md` 能导航到相关内容。
- 如果任务类型命中了 knowledge 入口，相关正文已经读取并吸收，不只停留在索引层。
- 新增 skill frontmatter 合规。
- 链接路径存在。
- 未删除或覆盖旧规则语义。
