# Before You Code（动手前协议）

## 四项前提

动手前必须锁定：

1. 问题对象：具体文件、场景、资源、记录、规范或 skill。
2. 真相来源：用户指定、本仓文件、Unity 状态、测试输出、日志、外部参考。
3. 目标入口/环境：当前项目、Unity Editor、`.spec`、`.spec/knowledge/features/project`、`openspec`、系统目录 `D:\codex-home`。
4. 验收口径：完成后用什么回到原始目标验证。

任一缺失，不得实施，只能继续查证或问最小问题。

用户给出外部参考路径、仓库、网页、文档或资源目录时，该来源必须被当轮精确读取或验证；在没有读到该来源、没有锁定其原设计入口和适用边界前，不得实施代码、配置、插件级或架构级改动。此时正确动作是继续查证；如果来源不可达或无法定位关键实现，必须拒绝实施并说明缺失的前提。

多参考源或“参考某工程后重构”的任务，还必须先锁定设计裁决标准：

1. **项目本体先行**：先提炼当前项目已有职责归属，包括入口、权威数据来源、系统访问方式、失败语义、保存/刷新位置和验收点；再列参考工程的同职责流程。当前项目已有职责归属只是候选，不是默认正确；如果它继承了旧单机、旧业务、旧资源或旧 UI 假设，必须列为重构候选。
2. **成熟框架校准**：涉及地基、生命周期、系统注册、资源、场景、存档、联机、事件或模块边界时，至少选一个成熟游戏框架作职责校准，例如 UE Gameplay Framework 或 Unity Game Framework。校准只看职责分层、生命周期和模块边界。
3. **原生能力优先**：Unity 或当前依赖已经提供的正式资产、组件、API、导入管线和序列化语义优先使用；只有原生能力无法表达项目需求时，才允许重构职责归属或新增作者源。
4. **职责内核优先于表面结构**：参考工程只能先提炼它解决的职责边界、权威数据来源、刷新/保存语义和验收位置；不得只因为参考工程有某个类、字段、目录或命名，就在本项目复制一层同形结构。
5. **偏离必须举证**：当前实现若偏离参考同职责流程或成熟框架职责分层，必须证明它服务当前项目新增职责、素材/资源形态、运行时入口或验收约束；证明不了的偏离默认视为退步、误改或待复核。
6. **重构职责归属优先**：发现已有职责归属不正确时，优先重构、拆分、迁移或删除该职责归属；不得用包装层、中转层、桥接层或并行模块绕开旧职责。
7. **单一真相源**：作者源数据、派生生成物、运行时状态、编辑器配置和验证报告不得互相代持；生成器不得把派生结果写回不该拥有它的源数据。
8. **约束匹配优先于“更通用”**：方案必须匹配当前阶段、素材形态、运行时入口、现有保存/刷新语义和用户已确认目标；不得为了显得架构完整而引入暂时不用的通用层。
9. **商业化扩展压力测试**：当前单机架构若未来要支持联机、Mod、热更新、关卡编辑器或创意工坊，必须说明该职责归属后续怎样扩展；说不清时先重构裁决，不进入实现。
10. **证据覆盖边界**：每个参考只能证明它实际覆盖的事实。外部源码、官方 API、当前项目代码、历史文档和测试结果必须分别标明。

这些标准没写清前，不得实施重构；不得先用“单例/接口/事件/Try 查询/依赖注入/必需依赖/可选依赖”等抽象词给方案定性。发现自己只是把外部参考或临时包装层套进项目时，必须先回到方案裁决。

多参考源输出必须明确：当前项目职责归属是什么、它是否正确；采用哪个参考的哪条职责、不采用哪条表面实现；成熟框架怎样分层；最终职责入口放在哪里；如果要重构，删除、迁移、拆分和替换哪些旧入口。若无法按以上标准排出优先级，只能停在方案比较或向用户确认，不得边实现边倒推理由。

## 读取顺序

1. 根 `AGENTS.md` 指针。
2. `.spec/AGENTS.md`。
3. `.spec/rules/system.md`。
4. `.spec/knowledge/README.md`。
5. 按任务类型读取 `.spec/knowledge/features/project/` 或对应 skill。

写业务代码、拆职责、加抽象、改运行时依赖、改 UI 绑定或碰 Unity 序列化资源时，还必须按 `.spec/knowledge/README.md` 命中并读取对应 standards；常见入口包括 `code-design`、`runtime-implementation-boundaries`、`unity-serialization-safety`。

## 规模判断

- 小任务：1 个文件或单一文档块，读直接相关规范后可直接改。
- 中任务：2-5 个文件或跨模块，先列改动清单，再逐项实施。
- 大任务：多模块、多阶段、有设计分歧，先用 `task-breakdown` 或 planning-with-files。

## 禁止

- 不把最近打开的 Unity 场景、最近日志或相似文件当成目标。
- 不为推进进度自行假设目标。
- 不顺手重构、不夹带新功能、不改任务外文件。
- 不用当前仓库搜索不到、历史规范里的参考名、或相似实现，替代用户当轮给出的外部参考路径。
- 不用“参考工程就是这么写的”“原生 API 能做到”“当前代码能跑”单独作为架构更优的理由；必须回到职责归属、生命周期、约束匹配和验收证据。
