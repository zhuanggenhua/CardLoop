# 开发与规范治理流程

## 工作前提

动手前必须锁定：

- 问题对象：本轮到底处理哪个文件、系统、场景、记录或规范。
- 真相来源：来自本仓文件、Unity Editor 状态、测试输出、日志、用户明确指定，还是外部参考。
- 目标入口/环境：在当前项目根、Unity Editor、`.spec/knowledge/features/project/`、`openspec/`、`.spec/` 还是全局 `D:\codex-home`。
- 验收口径：完成后回到哪里验证，使用什么证据证明。

当用户给出本地路径、外部参考工程、仓库、网页、文档或资源目录时，该来源优先级高于历史印象和当前仓库搜索结果。实施前必须读取或验证该精确来源，并锁定它的原设计入口、关键实现、数据/资源来源和适用边界；否则只能继续查证或拒绝实施。

## 多参考源设计裁决

涉及多个参考工程、Unity 原生能力、当前项目既有实现和用户设计意图时，必须先建立裁决标准，再提出或实施方案。默认顺序如下：

1. **项目本体先行**：先提炼当前项目已有职责归属，包括入口、权威数据来源、系统访问方式、失败语义、保存/刷新位置和验收点；再列参考工程的同职责流程。没有这张逐步对照，不得先用“单例/事件/接口/Try 查询/依赖注入/必需依赖/可选依赖”等抽象词给方案定性。当前项目职责归属只是候选，不是默认正确；如果它继承了旧单机、旧业务、旧资源或旧 UI 假设，就必须列为重构候选。
2. **成熟框架校准**：涉及地基、生命周期、系统注册、资源、场景、存档、联机、事件或模块边界时，必须至少选一个成熟游戏框架作职责校准，例如 UE Gameplay Framework 或 Unity Game Framework。校准只看职责分层、生命周期和模块边界，不照搬类名、目录名或引擎私有实现。
3. **原生能力优先**：Unity 或当前依赖已经提供的正式资产、组件、API、导入管线和序列化语义优先使用；只有原生能力无法表达项目需求时，才允许重构职责归属或新增作者源。
4. **职责内核优先于表面结构**：参考工程只能先提炼它解决的职责边界、权威数据来源、刷新/保存语义和验收位置；不得只因为参考工程有某个类、字段、目录或命名，就在本项目复制一层同形结构。
5. **偏离必须举证**：当前实现若偏离参考同职责流程或成熟框架职责分层，必须证明它服务当前项目新增职责、素材/资源形态、运行时入口或验收约束；证明不了的偏离默认视为退步、误改或待复核，不得倒推成“更规范”。
6. **重构职责归属优先**：发现已有职责归属不正确时，优先重构、拆分、迁移或删除该职责归属；不得用包装层、中转层、桥接层或并行模块绕开旧职责。新增代码只能是正式职责入口的组成部分，不能作为“临时第二套真相”存在。
7. **单一真相源**：每类数据只能有一个现实职责归属。作者源数据、派生生成物、运行时状态、编辑器配置和验证报告不得互相代持；生成器不得把派生结果写回不该拥有它的源数据。
8. **约束匹配优先于“更通用”**：方案必须匹配当前阶段、素材形态、运行时入口、现有保存/刷新语义和用户已确认目标；不得为了显得架构完整而引入暂时不用的通用层。
9. **商业化扩展压力测试**：当前单机架构若未来要支持联机、Mod、热更新、关卡编辑器或创意工坊，不能只做“单机先能跑”的结构。必须说明该职责归属后续怎样扩展；说不清时先重构裁决，不进入实现。
10. **证据覆盖边界**：每个参考只能证明它实际覆盖的事实。外部源码、官方 API、当前项目代码、历史文档和测试结果必须分别标明，不能混成一个“参考后就是最佳实践”的结论。

多参考源输出必须明确：当前项目职责归属是什么、它是否正确；采用哪个参考的哪条职责、不采用哪条表面实现；成熟框架怎样分层；最终职责入口放在哪里；如果要重构，删除、迁移、拆分和替换哪些旧入口。若无法按以上标准排出优先级，只能停在方案比较或向用户确认，不得边实现边倒推理由。

## 参考模块吸收门禁

参考模块的“吸收完成”指玩家可见能力已经由当前项目新正式框架接管，不是保留参考工程的类、字段和目录，也不是把多个参考实现拼成一套结构。

每个 StackCraft 一级模块必须按以下顺序收口：

1. 先列功能裁决：逐项区分“明确吸收的玩家可见功能”“只作为问题证据/体验参考”“明确排除的旧功能”。参考源码中存在的类、枚举、字段和未被真实内容使用的能力，不能自动进入吸收清单。
2. 再确定唯一架构：从当前游戏需求、现有正式职责、原生能力和成熟框架边界推导一条完整实现；参考工程只提供证据，不允许按来源各保留一块结构。
3. 使用新框架实现：正式代码不得依赖 StackCraft 运行时命名空间、旧单例、固定资源路径或旧场景入口。临时素材可以复用，但职责、状态和执行链必须归当前项目。
4. 在统一测试场景验收：默认追加到 `FoundationTest`；只有场景隔离确有必要时才建立专项测试场景。测试必须覆盖本模块明确选择吸收的同等玩家可见功能，以及新架构特有的职责边界。
5. 通过后进入下一一级模块：自动化测试、运行日志、场景状态或必要的人工交互证据必须能回到功能裁决逐项对账。只完成子模块文档、接口、静态结构或单元测试，不能越权宣布整个一级模块已吸收完成。

“实现相同功能”只要求功能和交互结果等价，不要求保留参考工程的结构。明确排除的自动触发、固定场景名、单例链、直接副作用、枚举扩展限制等旧行为，应在测试中证明没有进入正式链路，而不是为了表面一致重新实现。

## 执行边界

- 根 `AGENTS.md` 是入口，只放指针，不再堆项目细节。
- `.spec` 是规范结构主入口。
- `.spec/knowledge/features/project/` 是当前项目知识库正式入口；废弃目录不得作为规范入口继续引用。
- `openspec` 承载 proposal/change/spec，不混进 `.spec/decisions`。
- `.codex/skills` 和 `.agents/skills` 的现有项目 skill 继续可用；重复 skill 已在 `skill-conflicts.md` 收口。
- 参考工程接入或插件级抽象不得先写实现再补证据；如果外部参考路径尚未读取、关键入口尚未定位，必须停在“前提未锁定”，不能用“先做一个通用版本”代替参考裁决。

## LumioAgent 吸收边界

采用：

- `.spec` 结构分层。
- `spec-steward` 维护规范落点。
- `lessons.md` 作为反复错误升级池。
- “完成声明必须有验证证据”的收口门禁。
- “主 Agent 调度、skill 是方法、`.md` 是规则”的结构思想。

不采用：

- 默认创建或使用 git worktree 的流程。
- 未经用户确认的分支、提交、发布、PR 流程。
- 所有生产代码都必须严格 TDD 的一刀切规则。
- “设计文档必须提交”的默认动作。

## Git 与提交

- 不使用回滚/撤销历史操作。
- 不擅自创建、切换、重建或删除分支、tag、worktree。
- 不主动提交、不推送，除非用户当轮明确允许。
- 工作区已有无关改动时，只触碰本轮目标文件。

## 知识沉淀

- 新长期规则：先判断落点，再写入 `.spec/rules/`、`.spec/knowledge/standards/`、`.spec/skills/`、`.spec/knowledge/features/project/`、`openspec/` 或全局 `D:\codex-home`。
- 规范文档同样遵守单一真相源：具体执行口径只写在一个权威文档里；入口、索引、冲突矩阵只写摘要和链接，不能复制会漂移的模型配置、命令顺序、参数或验收清单。
- 调整某条规范时，先找权威文档，再同步所有引用处的摘要；如果发现多个文档都在承载同一口径，必须收口到一个权威文档，其他位置改成路由说明。
- 反复错误：第二次写入 `.spec/knowledge/lessons.md`，第三次左右升级。
- 项目事实或 Unity 入口：优先更新 `.spec/knowledge/features/project/` 对应分册，再由 `.spec/knowledge/README.md` 导航。
- 可复用 workflow：写入 `.spec/skills/` 或既有项目 `.codex/.agents/skills`，不要把详细 SOP 塞进根 AGENTS。
- 废弃入口：不得重建、引用或新增旧项目知识库目录作为规范目录；发现该目录存在时必须删除或说明具体外部占用。

## 结构校验

`.spec` 结构、索引、skill 或 agent 变化后，运行：

```powershell
node .spec/tools/spec-lint.mjs
```

该脚本只检查规范结构，不启动 Unity、不修改资产。
