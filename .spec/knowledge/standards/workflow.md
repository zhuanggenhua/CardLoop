# 开发与规范治理流程

## 工作前提

动手前必须锁定：

- 问题对象：本轮到底处理哪个文件、系统、场景、记录或规范。
- 真相来源：来自本仓文件、Unity Editor 状态、测试输出、日志、用户明确指定，还是外部参考。
- 目标入口/环境：在当前项目根、Unity Editor、`.spec/knowledge/features/project/`、`openspec/`、`.spec/` 还是全局 `D:\codex-home`。
- 验收口径：完成后回到哪里验证，使用什么证据证明。

当用户给出本地路径、外部参考工程、仓库、网页、文档或资源目录时，该来源优先级高于历史印象和当前仓库搜索结果。实施前必须读取或验证该精确来源，并锁定它的原设计入口、关键实现、数据/资源来源和适用边界；否则只能继续查证或拒绝实施。

## 多参考源设计裁决

涉及多个参考工程、Unity 原生能力、当前项目既有实现和用户设计意图时，必须先建立裁决标准，再提出或实施方案。默认顺序如下：

1. **同职责流程先行**：先列参考工程的同职责流程，包括入口、数据 owner、系统访问方式、失败语义、保存/刷新位置和验收点；再列当前项目的对应流程。没有这张逐步对照，不得先用“单例/事件/接口/Try 查询/依赖注入/必需依赖/可选依赖”等抽象词给方案定性。一个实现能通过审计，原因必须是它和参考同职责流程一致，或偏离已被当前项目约束证明为必要；不能因为用户当轮口头认可、当前代码能跑、或者看起来更“安全/规范”就判通过。
2. **原生能力优先**：Unity 或当前依赖已经提供的正式资产、组件、API、导入管线和序列化语义优先使用；只有原生能力无法表达项目需求时，才新增包装层、生成器或自定义资产类型。
3. **职责内核优先于表面结构**：参考工程只能先提炼它解决的职责边界、数据 owner、刷新/保存语义和验收位置；不得只因为参考工程有某个类、字段、目录或命名，就在本项目复制一层同形结构。
4. **偏离必须举证**：当前实现若偏离参考同职责流程，必须证明它服务当前项目新增职责、素材/资源形态、运行时入口或验收约束；证明不了的偏离默认视为退步、误改或待复核，不得倒推成“更规范”。
5. **最薄可行抽象**：能用现有 owner 加一个显式字段解决的，不新增独立 ScriptableObject、manager、桥接层或全局服务；只有当它有独立生命周期、跨系统复用、单独校验、热切换或内容生产闭包时，才升级为独立资产或模块。
6. **单一真相源**：每类数据只能有一个现实 owner。作者源数据、派生生成物、运行时状态、编辑器配置和验证报告不得互相代持；生成器不得把派生结果写回不该拥有它的源数据。
7. **约束匹配优先于“更通用”**：方案必须匹配当前阶段、素材形态、运行时入口、现有保存/刷新语义和用户已确认目标；不得为了显得架构完整而引入暂时不用的通用层。
8. **证据覆盖边界**：每个参考只能证明它实际覆盖的事实。外部源码、官方 API、当前项目代码、历史文档和测试结果必须分别标明，不能混成一个“参考后就是最佳实践”的结论。

多参考源输出必须明确：采用哪个参考的哪条职责、不采用哪条表面实现、当前项目的 owner 放在哪里、为什么这个方案比当前实现和其它候选更好。若无法按以上标准排出优先级，只能停在方案比较或向用户确认，不得边实现边倒推理由。

## 执行边界

- 根 `AGENTS.md` 是入口，只放指针，不再堆项目细节。
- `.spec` 是规范结构主入口。
- `.spec/knowledge/features/project/` 是当前项目知识库正式入口；废弃目录不得作为规范入口继续引用。
- `openspec` 承载 proposal/change/spec，不混进 `.spec/decisions`。
- `.codex/skills` 和 `.agents/skills` 的现有项目 skill 继续可用；重复 skill 已在 `skill-conflicts.md` 收口。
- 参考工程接入或插件级抽象不得先写实现再补证据；如果外部参考路径尚未读取、关键入口尚未定位，必须停在“前提未锁定”，不能用“先做一个通用版本”代替参考裁决。

## LumioAgent 吸收边界

采用：

- `.spec` 结构分层。
- `spec-steward` 维护规范落点。
- `lessons.md` 作为反复错误升级池。
- “完成声明必须有验证证据”的收口门禁。
- “主 Agent 调度、skill 是方法、`.md` 是规则”的结构思想。

不采用：

- 默认创建或使用 git worktree 的流程。
- 未经用户确认的分支、提交、发布、PR 流程。
- 所有生产代码都必须严格 TDD 的一刀切规则。
- “设计文档必须提交”的默认动作。

## Git 与提交

- 不使用回滚/撤销历史操作。
- 不擅自创建、切换、重建或删除分支、tag、worktree。
- 不主动提交、不推送，除非用户当轮明确允许。
- 工作区已有无关改动时，只触碰本轮目标文件。

## 知识沉淀

- 新长期规则：先判断落点，再写入 `.spec/rules/`、`.spec/knowledge/standards/`、`.spec/skills/`、`.spec/knowledge/features/project/`、`openspec/` 或全局 `D:\codex-home`。
- 规范文档同样遵守单一真相源：具体执行口径只写在一个 owner 文档里；入口、索引、冲突矩阵只写摘要和链接，不能复制会漂移的模型配置、命令顺序、参数或验收清单。
- 调整某条规范时，先找 owner，再同步所有引用处的摘要；如果发现多个文档都在承载同一口径，必须收口到一个 owner，其他位置改成路由说明。
- 反复错误：第二次写入 `.spec/knowledge/lessons.md`，第三次左右升级。
- 项目事实或 Unity 入口：优先更新 `.spec/knowledge/features/project/` 对应分册，再由 `.spec/knowledge/README.md` 导航。
- 可复用 workflow：写入 `.spec/skills/` 或既有项目 `.codex/.agents/skills`，不要把详细 SOP 塞进根 AGENTS。
- 废弃入口：不得重建、引用或新增旧项目知识库目录作为规范目录；发现该目录存在时必须删除或说明具体外部占用。

## 结构校验

`.spec` 结构、索引、skill 或 agent 变化后，运行：

```powershell
node .spec/tools/spec-lint.mjs
```

该脚本只检查规范结构，不启动 Unity、不修改资产。
