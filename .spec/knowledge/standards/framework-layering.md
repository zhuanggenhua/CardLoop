# 框架分层规范

本文件是 CardLoop 框架层级的唯一口径。涉及 YokiFrame、GameCore、Gameplay、外部参考候选、目录重切或代码重构前，先读这里，再读对应功能规范。

## 三层职责

依赖方向只能是：

    Gameplay -> GameCore -> YokiFrame

反向依赖不得出现：YokiFrame 不知道 GameCore / Gameplay，GameCore 不知道 Gameplay 或 CardLoop 具体业务。

### YokiFrame

YokiFrame 是底座层，只承载无游戏业务语义的基础设施：

- 生命周期、事件、异步、场景、资源、UI、存档等通用工具能力。
- 能离开 CardLoop 或任一具体游戏独立成立的框架原语。
- 插件自身公开 API、生成器和工具链入口。

YokiFrame 不承载卡牌、剧本、背包、配方、任务、战斗、职业、Mod 规则、联机席位或任何玩家可见业务规则。若为了某个游戏把业务概念塞进 YokiFrame，说明层级判断错误。

### GameCore

GameCore 是通用游戏解决方案层，基于 YokiFrame 组合出多个游戏可复用的能力：

- 存档槽位、资源门面、输入门面、音频门面、UI 面板栈、对象池、内容身份、数据库 / 索引、场景切换、游戏状态、命令 / 请求等通用游戏能力。
- 可被不同游戏配置或扩展的作者源、接口、抽象基类、数据容器和验证入口。
- 与具体游戏无关的错误语义、生命周期、加载/释放、版本和持久化边界。

GameCore 可以提供扩展点，但不能内置 CardLoop 的卡牌规则、来源项目字段、旧项目世界观、具体剧本数值、具体 UI 文案或项目素材地址。

### Gameplay

Gameplay 是 CardLoop 业务层，承载玩家可见规则和本项目作者内容：

- 卡牌生存、牌桌、牌堆、开卡包、配方、行动、剧本、任务、战斗、装备、职业、世界流程和本项目 UI。
- CardLoop 自己的玩家可见效果、业务取舍和内容规则。
- 具体 ScriptableObject 内容、Prefab、场景、资源地址、测试场景和验收链。

只要规则需要提到 CardLoop、某张卡、某个剧本、某个 UI 面板或具体资源，它就默认属于 Gameplay 或项目事实文档，不下沉到 GameCore，更不能下沉到 YokiFrame。

## GameCore 特化裁决

当感觉“GameCore 需要游戏特化”时，不默认提到 YokiFrame。按下面顺序裁决：

1. **无游戏语义的基础设施**：可直接离开任何游戏成立，放 YokiFrame。
2. **跨游戏通用能力**：至少能用同一小接口服务两个不同游戏形态，放 GameCore；特化点用接口、策略、作者源或数据模块暴露。
3. **本游戏业务规则**：依赖 CardLoop 产品、玩家可见语义、内容数值或资源形态，放 Gameplay。
4. **证据不足**：先写文档裁决和替换清单，不写代码、不建空接口、不加兼容壳。

正确模式是 **GameCore 暴露稳定扩展点，Gameplay 提供具体实现 / 数据 / 策略**。只有扩展点本身已经抽象到无游戏语义，才考虑继续下沉到 YokiFrame。

### 常见裁决示例

| 需求 | 默认落点 | 理由 |
|---|---|---|
| 存档槽位、文件版本、原子写入、模块容器 | GameCore | 多个游戏都需要同一文件层能力；具体保存哪些游戏事实由 Gameplay 模块提供。 |
| 背包 / 容器基础数据结构 | GameCore 候选 | 如果只表达物品集合、容量、增删和快照，可通用；若包含 CardLoop 卡牌、剧本、交易或职业规则，规则部分必须在 Gameplay。 |
| 卡包打开、牌堆合并、桌面放置、牌桌手感 | Gameplay | 这些是 CardLoop 玩家可见规则，不属于通用游戏框架。 |
| 输入 action 绑定、重绑定存储、输入启停 | GameCore | 属于多游戏可复用的输入门面；具体“拖卡”“确认行动”“打开存档面板”的解释在 Gameplay。 |
| EventKit、SceneKit、SaveKit、ResourceSystem 的原始插件能力 | YokiFrame | 无具体游戏语义，是底座原语。 |
| GameCore 对 YokiFrame 的薄封装 | GameCore 或删除 | 只有增加生命周期、错误语义、项目配置或跨游戏统一接口时才保留；纯转发应删除，不下沉成新的 Frame 能力。 |
| 具体游戏默认存档名、资源地址、UI 文案、测试场景 | Gameplay / 项目事实 | 这些依赖 CardLoop 当前产品和作者内容，不能进入 GameCore。 |

判断口诀：**特化不是下沉理由；通用合同才是 GameCore，游戏语义回 Gameplay，无游戏原语才回 YokiFrame。**

## 代码归属审查清单

后续开始代码重构时，每个待移动、删除或改名的文件先按下表登记，不登记清楚不得实施：

| 项 | 必填问题 |
|---|---|
| 当前文件 | 它现在在哪个目录、哪个程序集、由谁调用？ |
| 现实职责 | 它服务的是底座原语、通用游戏能力，还是 CardLoop 玩家规则？ |
| 权威状态 | 它是否持有可写状态；如果有，唯一写入口是谁？ |
| 参考来源 | 它来自 YokiFrame、GameCore、官方 skill、外部候选来源，还是 CardLoop 自有实现？ |
| 目标落点 | 保留在 YokiFrame / GameCore / Gameplay / 参考区 / 移出 active / 删除中的哪一个？ |
| 删除或迁移条件 | 被替代入口、消费者切换、验证命令和旧入口负向断言是什么？ |

如果一个文件同时回答出两个层级的职责，默认先拆职责或删除浅包装，不保留混合层。

## 参考来源口径

旧来源项目、官方 Unity skill 或其它外部资料，只是候选来源和证据，不是 CardLoop 的第二套真相源。

- 公共能力保持一致：插件公开 API、YokiFrame 基础原语、GameCore 通用合同和参考来源中已经验证成熟的通用能力，尽量沿用相同职责和命名。
- 项目特有必须抽取：来源工程的世界观、任务记录、测试截图、旧场景、旧流水账、旧业务数据和临时实现不能进入 CardLoop 框架规范。
- 参考候选要逐项说明：参考了什么、不参考什么、当前落点是什么、验证回到哪里。
- 来源特定长文不进入 active 项目文档；需要追溯时看 git 历史或外部来源本体，框架总口径只放本文件和对应 standards。

## 文档先于代码

框架、目录、职责或模块 owner 的重构，必须先完成文档收口，再进入代码重构。最低完成条件：

- 本文件或对应 standards 已写清唯一分层口径。
- `.spec/knowledge/README.md` 和必要项目索引能路由到唯一正文。
- 旧根级流水账、空文档或参考工程专项记录没有被当作当前代码重构真相源。
- 待重构文件已有代码归属审查清单，能说明保留、迁移、移出 active 或删除的依据。
- `node .spec/tools/spec-lint.mjs` 通过。

文档未收口时，可以继续补证据、改索引、移出 active 入口或删除真正垃圾；不得开始改运行时代码、Prefab、场景或 Unity 配置来抢先完成框架重构。
