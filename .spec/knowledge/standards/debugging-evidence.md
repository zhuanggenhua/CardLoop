# 排查证据链规范

本文件回答“反馈问题后先查什么、证据怎么分层、什么时候加日志、怎么汇报链路状态”。遇到 bug、异常行为、回归、资源缺失、表现不对或用户现场反馈时查；具体执行流程仍按 `.spec/skills/systematic-debugging`。

## 反馈保真

- 用户已经报出异常、回归、未播放、未生效、错位、卡住、资源为空等问题时，默认把它当作已成立的问题陈述开始排查；不要把“先证明 bug 存在”当作起手式。
- 保留用户描述中的关键限定词、状态、数量和范围。用户说“持续存在”时，不得用“也许只是一帧延迟”口头反驳，除非有同对象、同链路的后续帧证据。
- 用户已经明确冻结的事实，例如位置正确、只旋转错误、Prefab 本体字段为空、某个触发点已到达，必须优先作为当前真相处理；推翻它需要直接证据。

## 证据分层

- **静态代码证据**：证明逻辑结构、调用入口、条件门控和可能分支。
- **序列化配置证据**：证明资源、引用、组件字段、GUID、fileID、Prefab、场景 override 和作者源状态。
- **运行时日志证据**：证明调用发生、状态值、分支命中、生命周期和运行结果。
- **视觉证据**：截图、录像、Scene/Game 视图、可视化轨迹、Renderer bounds、相机视口坐标等，证明用户实际看到的表现。
- 不得把日志链路跑通说成资源本体正常；不得把静态配置正确说成运行态一定生效；不得把截图像某状态直接说成代码根因。

## 静态优先

- 起手先用 `rg` 搜脚本名、场景名、节点名、方法名、组件名、资源名、文案关键词。
- 先读代码、资源、Prefab、场景、文档和引用关系，把静态证据能确认的事实先确认完。
- 只有静态证据不足以区分互斥结论、缺少关键运行态状态，或修复后需要验收时，才升级到日志、Play Mode、截图或其它动态取证。
- 单一 UI 布局、尺寸、间距、字段、引用或资源本体问题，如果序列化证据足够，不用先进入播放态。

## 链路分段

排查必须拆链，不用一句“正常 / 有问题”收口。常用分段：

- 入口链：谁触发、何时触发、触发条件是什么、是否到达首个有效处理点。
- 状态链：状态由谁写入、谁持有、谁覆盖、谁消费，是否存在双写或第二套真相。
- 绑定链：真正执行、真正出图、真正生效的组件、子节点、资源实例或运行时对象是谁。
- 资源链：Prefab / Material / Sprite / Texture / UI / 粒子本体是否存在、字段是否指向正确 GUID / fileID。
- 时序链：生命周期、切场、销毁、协程、动画、Timeline、Gate、显隐恢复的边界是否一致。
- 表现链：最终画面异常是状态没到、引用没绑、资源没加载、条件没满足，还是表现层自身问题。

汇报推荐写成分段状态，例如：`入口已确认 / 资源本体未确认 / 生成已确认 / 物理落地已确认 / 拾取未确认 / 画面未确认`。

## 日志取证

- 当静态检查后仍出现 `可能`、`怀疑`、`大概率` 且断点位于运行链内部，必须补最小必要日志或等价运行时证据。
- 同一问题连续两次未解决，且静态分析仍无法唯一确认断点，下一步默认必须升级为日志取证，不能继续猜第三轮。
- 日志必须全面、精确、可搜索：覆盖所有尚未排除的关键断点；只打印能排除假设的关键字段；同一链路使用同一个稳定中文前缀。
- 日志噪声要可控。循环、每帧、每实例、对象池内部状态和粒子数量等高频日志只能作为临时诊断；拿到证据后收敛或删除。
- 跨场景、销毁、协程中断或生命周期边界问题，第一轮日志要先建立不会随源对象销毁的稳定载体，再补局部点位。

## 资源与视觉问题

- Prefab、Sprite、Material、Texture、粒子或 UI 本体为空、预览异常、Inspector 字段为空时，先查本体字段、材质、shader、导入器和 GUID / fileID。
- 掉落、拾取、奖励、弹体、UI 飞行动画这类链路必须同时核对世界对象本体出图链和 UI / 结算表现链。
- 涉及世界物体飞向 HUD、背包、血条或 Canvas 时，必须做坐标空间审计：源对象、目标宿主、Canvas 模式、父节点、`anchoredPosition`、`localScale`、`sizeDelta`、anchor / pivot 和 CanvasScaler。
- 涉及视觉幅度、轨迹、遮挡、大小、速度感或手感时，没有截图、录像或可视化证据，只能结论到调用链和数值状态，不能声称画面已正常。

## 回归与自改动归因

- 用户提示“最近改动引入”“直接看 diff”“之前是好的”时，起手先读取自己本轮或最近相关 diff，列出哪些写入最直接影响症状。
- 正确改动和错误改动必须分账。保留已被证据证明正确的修复，只撤回或继续验证实验性、范围外或引入副作用的改动。
- 修完根因后，按关键词、模式、脚本结构或资源类型横向搜索同类问题；同类问题无法安全处理时，记录到对应清单或汇报中。

## Unity 崩溃取证

Unity 验证流程、启动纪律和端到端标准以 [`testing.md`](testing.md) 为唯一正文。本节只规定 Unity 已经疑似崩溃后的取证口径。

- 先确认现实后果：Unity 是长时间导入 / 编译、窗口无响应、进程退出，还是 Windows / Unity Crash Handler 已生成崩溃记录。
- 先读证据再归因：检查项目 `Logs/`、Unity 崩溃目录、Windows Application 事件、CrashDumps、最近 Editor log 和当前 Unity / AssetImportWorker / UnityShaderCompiler 进程。
- 汇报时必须把“用户看到的现象”和“日志里的触发模块”分开。比如“窗口卡住”不等于“进程崩溃”，“PapiV8.dll 崩溃”不等于“Gameplay 代码崩溃”。
- 崩溃未分类前不得继续实现、跑同一路径测试或启动新的普通 Editor；只能继续只读取证，或提出最小补救动作。
- 清理缓存、crash dump 或强杀进程都不是默认排查动作。当前项目的 `Temp/UnityLockfile` 若已被证明是无 Unity / 导入 / shader 编译进程时留下的残留，并且正在阻塞原验证入口，可通过 `node .spec/tools/unity-verify.mjs clean-stale-lockfile --confirm-stale-lockfile` 清理；其它清理仍需单独证据。
