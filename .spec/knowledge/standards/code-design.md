# 代码设计原则

本文件回答“代码结构该怎么设计、什么时候该用设计模式、哪些反模式必须避免”。它不替代 [`gameplay-architecture.md`](gameplay-architecture.md) 的 Gameplay 专项对象模型，也不替代 [`code-style.md`](code-style.md) 的命名、注释和生成物规范。

## 何时查

- 新增或改写业务代码、编辑器工具、运行时服务、ScriptableObject 作者源、UI 绑定或测试夹具前。
- 准备新增接口、抽象类、工厂、策略、事件、服务、管理器、上下文、注册表、缓存或包装层前。
- 审查代码是否存在上帝类、魔法字符串、复制粘贴、第二套真相、临时桥接层、过度接口或防护性架构时。
- 如果问题涉及 Gameplay 模块边界、对象模型、继承 / 组合、单局生命周期、Mod、联机或 StackCraft 吸收，必须继续读 [`gameplay-architecture.md`](gameplay-architecture.md)。

## 基本原则

- **单一职责原则（SRP）**：一个类、资源、工具或服务只能有一个清晰职责和一个主要修改理由；UI 组件只做表现和交互映射，作者源只描述可配置事实，运行时聚合只提交自己的状态变化。
- **开闭原则（OCP）**：新增内容、行动、面板、文本映射、配置项或规则分支时，优先通过作者源、注册表、映射、组合对象或正式扩展点接入；不得让核心分发器不断膨胀成大型 `if/else` / `switch`。
- **里氏替换原则（LSP）**：同一基类、接口或同类配置项必须遵守同一运行契约；调用方不能依赖某个派生类型、特殊层级、特殊字段默认值或隐藏副作用才能正确工作。
- **接口隔离原则（ISP）**：只暴露调用方真实需要的能力；不得把整个管理器、整棵场景树、整份上下文对象或全部服务集合传给下游。
- **依赖倒置原则（DIP）**：高层流程依赖稳定职责入口、作者源、聚合根、清晰接口或正式服务，而不是深层节点路径、临时对象名、具体 Prefab 层级或旁路实现细节。
- **迪米特法则 / 最少知识原则**：对象只和自己的直接 owner、直接协作者或正式入口交互；不得跨多层 `A.B.C.D` 读取或修改远端状态。

## 项目补充原则

- **DRY**：同一逻辑、同一绑定规则、同一验证规则、同一映射关系只保留一个权威实现；复制后微调默认视为边界问题。
- **KISS**：优先选择能解释当前需求的最小结构；复杂度必须换来更清楚的职责、生命周期、验收或扩展边界。
- **YAGNI**：不为“以后也许会用”创建空接口、空系统、空上下文、预留状态、防重表或兼容壳。
- **单一真实来源**：内容定义、运行时状态、表现投影、资源地址、输入、事件、存档和校验都必须有唯一 owner；派生缓存只能生成或校验，不能成为第二份作者真相。
- **组合优先但不教条**：可动态添加 / 移除 / 叠加的能力优先组合；稳定身份关系优先用清晰继承或领域对象承载。具体裁决按 [`gameplay-architecture.md`](gameplay-architecture.md) 的继承与组合门禁执行。

## 设计模式使用规则

设计模式只能解决已证明存在的职责问题，不能作为“看起来更专业”的默认架构。

| 模式 | 允许使用 | 禁止滥用 |
|---|---|---|
| 注册表 / 映射 | 内容 ID、文本 key、行动定义、面板入口、资源清单等需要稳定查询和扩展时。 | 把运行时可变状态塞进注册表，或用注册表替代作者源校验。 |
| 工厂 | 实例化过程需要统一资源加载、初始化、校验、生命周期绑定或测试替换时。 | 只包一层 `new` / `Instantiate`，没有减少调用方知识。 |
| 策略 | 同类规则存在多个可替换算法，且选择来源可由作者源、配置或正式状态解释时。 | 为尚不存在的未来规则提前建空接口。 |
| 观察者 / 事件 | 已提交事实需要通知多个只读消费者，且订阅和注销生命周期清楚时。 | 用事件驱动命令流程、隐藏顺序依赖，或建立第二事件总线。 |
| 状态机 | 对象确实有互斥状态、显式转移、进入 / 退出动作和非法转移时。 | 用一堆布尔值和兜底分支伪装状态机，或让动画参数替代规则状态。 |
| 对象池 | 高频创建 / 销毁对象造成明确分配、GC 或性能压力时。 | 稀有对象、生命周期简单对象或资源真相不清时提前池化。 |
| 适配器 / 包装层 | 连接第三方 API、跨模块稳定边界、权限校验、回放记录、生命周期转换等真实职责时。 | 只转发方法名、掩盖旧职责没有重构、形成临时桥接层；CardLoop 内部系统关系不得被命名或汇报成外部项目适配壳。 |

需要更细的 Unity 模式选择时，读取项目 UnitySkills 模块：`.spec/skills/unity-skills/skills/patterns/MODULE.md`。涉及模块边界、SOLID、职责拆分和结构性重构时，读取 `.spec/skills/unity-skills/skills/architecture/MODULE.md` 和 `.spec/skills/unity-skills/skills/scriptdesign/MODULE.md`。

## 反模式清单

- **上帝类 / 上帝管理器**：一个类同时拥有内容扫描、对象创建、运行状态、UI、存档、事件、随机、资源和规则结算。
- **魔法数字 / 魔法字符串**：场景名、对象路径、资源地址、文本 key、状态名、动作名散落在业务代码中。
- **复制粘贴式编程**：复制同类对象、同类面板、同类规则或同类工具后改少量字段，导致修一处必须同步多处。
- **第二套真相**：作者源、运行时状态、表现层、缓存、索引或测试夹具同时维护同一事实。
- **临时桥接层转正**：为了先跑通写的兼容层、中转层、包装层、影子状态、双命名兼容长期留在正式链路。
- **内部职责误称桥接**：CardLoop 是当前游戏本体，不是外部项目适配壳；除第三方插件官方扩展点或迁移兼容确有必要外，不得把本项目内部系统关系称为“桥接”，也不得用桥接命名掩盖正式模块边界缺失。
- **浅包装**：模块接口几乎等于实现细节，删除后复杂度直接消失，而不是回到多个调用方。
- **霰弹式修改**：一个小需求需要改很多不相干文件，说明职责边界或单一入口没有收口。
- **深层层级耦合**：业务代码依赖固定父子层级、长路径查找、对象名猜测或 `Find*` 类全局查询作为正式依赖入口。
- **静默兜底 / 防护性架构**：内部不变量被破坏时返回假成功、自动修正、吞异常、使用 fallback、预留冲突表或防重集合掩盖真正入口错误。

发现反模式时，先按通用裁决阶梯处理：不做、删除、审查现有职责、重构 / 迁移、改作者源 / 配置，最后才新增正式入口。需要架构深化时读取 `D:\codex-home\skills\improve-codebase-architecture\SKILL.md`。

## 动手前自检

新增抽象、模式或防护代码前，至少回答：

1. 这个职责的 owner 是谁，生命周期由谁开始和结束？
2. 状态写入口是否唯一，消费者是否只读？
3. 删除这个模块后，复杂度会消失，还是会重新分散到多个调用方？
4. 有没有当前真实调用入口和验收点，还是只服务未来想象？
5. 它是否和现有 GameCore、Gameplay、EX-GAS、ResourceSystem、EventKit、UIKit 或 Unity 原生能力重复？
6. 它失败时是内部契约错误、正常业务拒绝、外部输入失败，还是可恢复系统故障？

答不清时不得新增抽象。先回到职责归属、作者源和正式入口裁决。
