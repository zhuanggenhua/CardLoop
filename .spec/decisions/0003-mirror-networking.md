# 0003 · 联机后端裁决:Mirror

- 日期:2026-08-27
- 状态:生效

## 背景

CardLoop 的首版联机目标已收窄为 2-10 人小规模朋友局,安全性和反作弊要求不高。项目仍需要合作生存、牌桌状态、行动结算、资源变化、随机结果、秘密信息和 Mod / 内容包版本保持一致,但不需要在首版为所有玩法预留竞技级客户端预测或复杂专服部署。

上一条 FishNet 裁决偏向“未来可上专服、预测校正和复杂联机扩展”的长期余量。根据当前产品口径,首版更应优先选择学习成本低、资料成熟、Host 房主局足够直接、低频权威命令容易落地的方案。

选择依据:

- Mirror 官方模型覆盖服务器权威、Host 房主模式和独立服务器;小规模合作局不需要为了牌桌低频操作引入更重的预测框架。
- Mirror 的 `Command`、`SyncVar`、`ClientRpc`、`TargetRpc` 能表达“客户端提交操作意图,房主 / 服务器确认结果,再同步给对应客户端”的首版联机链路。
- CardLoop 当前 2-10 人、低安全要求和牌桌 / 行动 / 资源等低频同步形态,更看重首版落地成本和可维护性,而不是一开始就为高频竞技同步优化。
- FishNet 仍保留为未来升级候选,但不再作为当前正式后端。

## 决策

CardLoop 未来首版正式 Unity 联机后端改用 Mirror。Mirror 承担连接、玩家对象、Host / Server / Client 生命周期、远程调用和状态同步;玩法规则仍由现有 `ScenarioRun`、`Tabletop`、行动实例、任务日志、战斗对象和内容 / Mod 版本边界拥有。

权威边界:

- 牌桌卡牌位置、工位归属、行动计划、回合确认、行动进度和结算结果由房主 / 服务器确认。
- 资源、角色状态、EX-GAS 能力和 GameplayEffect 结果由房主 / 服务器确认。
- 随机推进、掷骰结果、叛徒秘密状态、可见性和 Mod / 内容包版本由房主 / 服务器确认。
- 客户端可以生成拖拽预览、行动候选和本地表现,但不能直接写上述权威状态。

首版同步边界:

- 牌桌拖拽、行动提交、日程推进、资源变化、任务进度和普通战斗结果按低频命令 / 结果同步处理。
- 即时战斗中如果出现移动、瞄准等高频表现,先按当前真实玩法复审是否需要客户端预测;没有证据前不预建预测层。
- 秘密信息不依赖网络库自动解决。Host 进程天然能访问完整状态,因此首版只承诺普通客户端的可见性过滤;如果未来需要更强公平性或反作弊,再重新评估专服优先和 FishNet / 其它方案。

## 后果

当前不做:

- 不立即安装或接入 Mirror。
- 不提前创建 `NetworkBehaviour`、`Command`、`SyncVar`、`ClientRpc`、`PlayerId`、权限表或网络 DTO。
- 不把现有 `GameCommandContext.RemotePlayer` 当作联机协议。
- 不为了未来预测能力复制一套伤害、资源、命中或技能结算规则。

接入前提:

- 只有在玩家席位、可控制角色集合、队长授权、叛徒可见性、Host / Server 模式和断线策略形成正式事实后,才开始接入 Mirror。
- 接入时先让 Mirror 承担连接、生成、同步和生命周期,再把权威命令接入现有 `ScenarioRun` / `Tabletop` 聚合;网络组件不能接管玩法规则。
- 如果后续确认需要严肃专服反作弊、竞技级客户端预测、复杂重连恢复或更高并发,再新增 ADR 重新评估 FishNet 或其它后端。

资料依据:

- Mirror 官方文档:服务器权威、Host / Server / Client 模式、`Command`、`SyncVar`、`ClientRpc`、`TargetRpc` 和兴趣管理。
- FishNet 官方文档:候选对比来源;其服务器权威、监听服务器、独立服务器和 `Replicate` / `Reconcile` 能力保留为未来升级参考。
- Unity Netcode for GameObjects 和 Photon Fusion 官方资料:候选对比来源;本轮不采用其作为当前正式后端。
