# 0004 · 联机薄协议骨架先行

- 日期:2026-08-27
- 状态:生效

## 背景

0003 已裁决首版联机后端采用 Mirror，但当时尚未形成执行授权，因此明确不立即创建网络 DTO、玩家席位或 Mirror 运行时代码。

现在用户明确要求开始联机准备。项目仍未安装 Mirror，也尚未确定完整玩家控制权、叛徒可见性、断线恢复和房间产品流程。直接接入 Mirror 运行时代码会把 `NetworkBehaviour`、`Command`、`SyncVar` 和 Rpc 生命周期提前扩散到 Gameplay 玩法层；继续完全等待业务定稿则会让单机实现默认全局可见、全权拖拽和裸随机，后续联机返工更大。

## 决策

先建立 Mirror 无关的 CardLoop 薄联机协议骨架，不安装 Mirror，不创建 `NetworkBehaviour`，不改场景、Prefab 或包清单。

本阶段允许创建以下项目侧协议事实：

- 玩家席位 ID、席位表和旁观者 / 玩家基本区别。
- 房主 / 服务器确认后的权威状态版本。
- 客户端牌桌命令信封，包含发起席位、客户端命令序号、期望权威版本和牌桌意图。
- 牌桌命令预测口径：本地表现、确定性状态预测、等待权威确认。
- 权威快照可见范围：公开快照和指定席位私有快照。
- 命令确认 / 拒绝回执及最小拒绝原因。

玩法规则仍由 `ScenarioRun`、`Tabletop`、行动实例、任务日志、战斗对象和内容 / Mod 版本边界拥有。薄协议骨架只定义网络外壳和联机语义，不复制伤害、资源、抽牌、行动结算、随机或可见性规则。

## 后果

接受的好处：

- 后续 Mirror 适配器只需要把 `[Command]`、`ClientRpc`、`TargetRpc` 映射到协议对象，不需要让玩法对象继承网络组件。
- 单机、EditMode 测试、存档恢复、AI 调试和未来 Mirror Host 局可以共享同一类“玩家请求 -> 权威确认 -> 可见快照”语义。
- 随机、隐藏信息和日终结算默认等待房主 / 服务器确认，不会因为乐观表现提前泄露。

接受的限制：

- 本阶段不证明 Mirror 包可安装、不证明 Unity 编译、不证明 Host / Client 能连接。
- 本阶段不实现完整控制权表、叛徒可见性、断线重连、网络序列化、快照差量或客户端回滚。
- 如果后续产品确定需要竞技级预测、高频物理同步或严肃反作弊，仍需要新增 ADR 复审 Mirror / FishNet / NGO / Fusion 选型。
